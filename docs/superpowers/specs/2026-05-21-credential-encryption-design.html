Credential Encryption at Rest

Bot tokens and CalDAV passwords encrypted in SQLite using AES-256-GCM before any OAuth tenant can be stored.

Issue #45 Branch: v2 Sprint 3 Status: Approved

2026-05-21  ·  Blocks: #46 OAuth installation flow

Overview

The multi-tenant SQLite schema (#44) stores workspaces.bot_token and caldav_credentials.password as plaintext. Before the OAuth installation flow (#46) goes live, those columns must be encrypted at rest.

A single new module — src/crypto.js — owns all encryption logic. The db.js layer calls it transparently: callers always pass and receive plaintext; the encoded blob never leaves db.js. A startup guard in server.js validates the ENCRYPTION_KEY env var before any DB operation can occur.

🔐
No external dependencies. The implementation uses only Node.js's built-in node:crypto module — AES-256-GCM with a random 12-byte IV per value. Key rotation is deferred to v2.

Locked Decisions

Decision Choice Rationale
Cipher AES-256-GCM Authenticated encryption — integrity and confidentiality in one primitive. Node.js built-in, no deps.
IV size 12 bytes (random per value) GCM standard recommendation. Random per-value IV means identical plaintexts produce different ciphertexts.
Storage format iv_hex:ct_hex:tag_hex Human-readable in a hex editor, easy to parse with split(':'), no binary encoding overhead.
Key read timing At call time, not module load Allows tests to set process.env.ENCRYPTION_KEY in setup without import-order problems.
Encryption boundary Transparent in db.js Single enforcement point. No caller can accidentally write plaintext to a sensitive column.
Column renaming Keep bot_token, password Encryption is transparent; leaking the encoding into column names would be an implementation detail in the schema. No migration needed.
Key rotation Out of scope (v1) Adds significant complexity. Deferred until the tenant count justifies it.

Architecture

src/crypto.js

Pure utility module. Three exports, no state. Reads process.env.ENCRYPTION_KEY at call time so tests can inject a key in beforeEach without import-ordering issues. 

const { createCipheriv, createDecipheriv, randomBytes } = require('node:crypto');

const KEY = () => Buffer.from(process.env.ENCRYPTION_KEY, 'hex');

function encrypt(plaintext) {
  const iv  = randomBytes(12);
  const cipher = createCipheriv('aes-256-gcm', KEY(), iv);
  const ct  = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();
  return `${iv.toString('hex')}:${ct.toString('hex')}:${tag.toString('hex')}`;
}

function decrypt(stored) {
  const [ivHex, ctHex, tagHex] = stored.split(':');
  const decipher = createDecipheriv('aes-256-gcm', KEY(), Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  return decipher.update(Buffer.from(ctHex, 'hex')) + decipher.final('utf8');
}

function validateEncryptionKey() {
  const key = process.env.ENCRYPTION_KEY;
  if (!key || !/^[0-9a-fA-F]{64}$/.test(key)) {
    throw new Error(
      'ENCRYPTION_KEY must be a 64-character hex string (32 bytes). ' +
      'Generate one with: openssl rand -hex 32'
    );
  }
}

module.exports = { encrypt, decrypt, validateEncryptionKey };
⚠️
Auth tag integrity. AES-256-GCM's auth tag covers both the ciphertext and any associated data. A tampered ciphertext causes decipher.final() to throw — callers should not catch that error silently.

db.js changes

Four targeted modifications. The rest of db.js is unchanged.

upsertWorkspace() — encrypt on write:

// existing function, one line changed:
const { encrypt, decrypt } = require('./crypto.js');
...
.run(teamId, teamName, botToken ? encrypt(botToken) : null, ...);

getWorkspace() — decrypt on read:

function getWorkspace(db, workspaceId) {
  const row = db.prepare('SELECT * FROM workspaces WHERE team_id = ?').get(workspaceId) || null;
  if (row?.bot_token) row.bot_token = decrypt(row.bot_token);
  return row;
}

New upsertCaldavCredentials():

function upsertCaldavCredentials(db, workspaceId, username, password) {
  db.prepare(`
    INSERT INTO caldav_credentials (workspace_id, username, password)
    VALUES (?, ?, ?)
    ON CONFLICT (workspace_id) DO UPDATE SET
      username = excluded.username,
      password = excluded.password
  `).run(workspaceId, username, encrypt(password));
}

New getCaldavCredentials():

function getCaldavCredentials(db, workspaceId) {
  const row = db.prepare(
    'SELECT username, password FROM caldav_credentials WHERE workspace_id = ?'
  ).get(workspaceId);
  if (!row) return null;
  return { username: row.username, password: decrypt(row.password) };
}
✓
Single enforcement point. Every write path for sensitive columns goes through these two functions. Future code that needs to store a bot token or CalDAV password calls upsertWorkspace() or upsertCaldavCredentials() — encryption is automatic.

server.js — startup validation

First line of start(), before openDb(). If ENCRYPTION_KEY is missing or malformed, the process throws and the server never starts — no partial state is possible. 

const { validateEncryptionKey } = require('./crypto.js');

async function start() {
  validateEncryptionKey();   // ← throws if key is absent or not 64-char hex
  const dataDir = process.env.DATA_DIR;
  ...
}

config.js — call-site updates

Two raw SQL fragments in config.js are replaced with calls to the new db.js functions. config.js does not import crypto.js.

seedWorkspace() — replace direct INSERT:

// Before:
db.prepare(`INSERT INTO caldav_credentials ... VALUES (?, ?, ?)`)
  .run(workspaceId, creds.username, creds.password);

// After:
upsertCaldavCredentials(db, workspaceId, creds.username, creds.password);

loadConfigFromDb() — replace direct SELECT:

// Before:
const creds = db.prepare('SELECT username, password FROM caldav_credentials WHERE workspace_id = ?').get(workspaceId);

// After:
const creds = getCaldavCredentials(db, workspaceId);

Ciphertext Format

All encrypted values stored in SQLite use the colon-delimited hex format: 

{iv_hex}:{ciphertext_hex}:{tag_hex}

Example (32-char IV | variable CT | 32-char tag):
a3f2c1d4e5b6a7f8c9d0e1f2:6e6f747468657265616c7061737377:8f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c

IV is always 24 hex chars (12 bytes). Auth tag is always 32 hex chars (16 bytes). Ciphertext length equals plaintext length (AES-GCM is a stream mode).

Why not Base64?

Base64 is slightly more compact (~33% overhead vs ~100% for hex), but the colon-delimited format is self-describing and trivially parseable without a library. For short values like tokens and passwords, the size difference is negligible. Hex is also easier to inspect in SQLite Browser or a shell.

Why not JSON?

JSON adds ~3× overhead for field names, requires JSON.parse/stringify, and offers no structural benefit over the colon format for a fixed 3-field tuple.

Testing Strategy

New: test/crypto.test.js

  • ☐ Round-trip: decrypt(encrypt(s)) === s for typical token and password values
  • ☐ Unique ciphertext: encrypt(s) !== encrypt(s) (random IV)
  • ☐ Tamper detection: flipping a byte in the ciphertext causes decrypt() to throw
  • ☐ validateEncryptionKey() throws on: missing key, 63-char key, 65-char key, non-hex chars
  • ☐ validateEncryptionKey() passes on valid 64-char lowercase hex

Updates to existing test files

Any test file that exercises upsertWorkspace() or upsertCaldavCredentials() needs ENCRYPTION_KEY in scope: 

// At the top of test/db.test.js, test/config.test.js
process.env.ENCRYPTION_KEY = '0'.repeat(64); // 64-char hex, valid test key

Additional assertions to add:

  • ☐ After upsertWorkspace(), the raw stored value of bot_token differs from the plaintext input
  • ☐ After upsertCaldavCredentials(), the raw stored value of password differs from the plaintext input
  • ☐ getWorkspace() returns the original plaintext
  • ☐ getCaldavCredentials() returns the original plaintext password
⚡
Do not use a null or all-zeros key in production. The test key '0'.repeat(64) is intentionally weak — it is only valid in test files that use an in-memory database. The Fly.io secret must be generated with openssl rand -hex 32.

Out of Scope

  • ✗ Key rotation — deferred to v2 milestone
  • ✗ Encrypting other columns (e.g. caldav_url) — not sensitive enough to warrant encryption overhead
  • ✗ KMS / HSM integration — single symmetric key is sufficient for v1
  • ✗ Per-workspace keys — single server-side key covers all tenants in v1
