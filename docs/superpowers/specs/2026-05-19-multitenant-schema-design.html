#44 — Multi-Tenant SQLite Schema &
Per-Workspace Config API

Design spec · v2 branch · 2026-05-19

Locked Decisions

Decision Choice Status

Overview

The v2 branch evolves the bot from a single-tenant GitHub Actions script into a multi-tenant Slack app. Every piece of state — calendar events, channel config, credentials — must be scoped to a workspace ID (Slack's team_id).

This issue (#44) lays the database foundation. It is a prerequisite for every other v2 issue: #45 (encryption), #46 (OAuth), #47 (per-workspace cron), #48 (onboarding wizard).

Scope boundary: This issue does not implement encryption (#45), OAuth token storage (#46), or multi-workspace cron scheduling (#47). Those build on top of this schema.

Schema

Nine tables total: four existing (recreated with composite PKs) + five new config tables.

Existing tables — recreated

These tables existed in the single-tenant schema but lacked workspace_id. The migration strategy drops them and recreates them with correct composite primary keys.

New config tables

Full SQL — config tables 
CREATE TABLE workspaces (
  team_id       TEXT PRIMARY KEY,
  team_name     TEXT NOT NULL,
  bot_token     TEXT,            -- plaintext; #45 encrypts
  installed_by  TEXT,
  installed_at  TEXT NOT NULL,
  active        INTEGER NOT NULL DEFAULT 1,
  locale        TEXT,            -- workspace default, e.g. 'en-US'
  timezone      TEXT,            -- IANA timezone, e.g. 'Europe/Berlin'
  error_channel TEXT,            -- channel_id for error routing
  nextcloud_url TEXT             -- optional, display only
);

CREATE TABLE caldav_credentials (
  workspace_id TEXT PRIMARY KEY,
  username     TEXT NOT NULL,
  password     TEXT NOT NULL,  -- plaintext; #45 encrypts
  FOREIGN KEY (workspace_id) REFERENCES workspaces(team_id)
);

CREATE TABLE calendars (
  workspace_id       TEXT NOT NULL,
  calendar_id        TEXT NOT NULL,  -- slug e.g. "team", "vorstand"
  name               TEXT NOT NULL,
  caldav_url         TEXT NOT NULL,
  caldav_metadata_url TEXT,
  color              TEXT,
  PRIMARY KEY (workspace_id, calendar_id),
  FOREIGN KEY (workspace_id) REFERENCES workspaces(team_id)
);

CREATE TABLE channels (
  workspace_id          TEXT NOT NULL,
  channel_id            TEXT NOT NULL,
  name                  TEXT,
  canvas_id             TEXT,
  canvas_url            TEXT,
  locale                TEXT,
  view                  TEXT,
  event_detail          TEXT,
  digest_style          TEXT,
  digest_format         TEXT,
  digest_schedule       TEXT,
  daily_digest_schedule TEXT,
  show_empty_days       INTEGER,
  notifications         TEXT,
  PRIMARY KEY (workspace_id, channel_id),
  FOREIGN KEY (workspace_id) REFERENCES workspaces(team_id)
);

CREATE TABLE channel_calendars (
  workspace_id TEXT NOT NULL,
  channel_id   TEXT NOT NULL,
  calendar_id  TEXT NOT NULL,
  PRIMARY KEY (workspace_id, channel_id, calendar_id),
  FOREIGN KEY (workspace_id, channel_id) REFERENCES channels(workspace_id, channel_id),
  FOREIGN KEY (workspace_id, calendar_id) REFERENCES calendars(workspace_id, calendar_id)
);

Migration Strategy

openDb() reads PRAGMA user_version immediately after opening the database. If the version is 0 (old single-tenant schema or a completely fresh file), it runs the v1 migration inside a transaction.

Data loss on upgrade: The migration drops the four old operational tables (events, color_cache, run_state, pending_notifications). This is intentional — v2 has never been deployed to production, so no real data is at risk. Operational data regenerates on the next CalDAV fetch and cron run. Config data is seeded via seedWorkspace(). 
// Inside openDb(), after pragma WAL:
const version = db.pragma('user_version', { simple: true });
if (version === 0) {
  db.exec(`
    DROP TABLE IF EXISTS events;
    DROP TABLE IF EXISTS color_cache;
    DROP TABLE IF EXISTS run_state;
    DROP TABLE IF EXISTS pending_notifications;
    -- create all 9 tables with new schema
    -- ...
    PRAGMA user_version = 1;
  `);
}

Future schema changes increment user_version further (2, 3, …) with their own migration blocks. This pattern is established here and used by all subsequent issues.

config.js API

loadConfigFromDb(db, workspaceId)

Assembles the same config object shape that loadConfig() produces, sourcing data from the new config tables. Throws a clear error if the workspace is not found. 

async function loadConfigFromDb(db, workspaceId) {
  // 1. getWorkspace(db, workspaceId) — throws if not found
  // 2. SELECT from caldav_credentials WHERE workspace_id = ?
  // 3. SELECT from calendars WHERE workspace_id = ? → build calendars dict
  // 4. SELECT from channels WHERE workspace_id = ? → for each channel,
  //    SELECT calendar_ids from channel_calendars → build channels array
  // Returns:
  return {
    workspace_id: row.team_id,
    locale: row.locale,         // from workspaces.locale
    timezone: row.timezone,     // from workspaces.timezone
    error_channel: row.error_channel,  // from workspaces.error_channel
    caldav_credentials: { username, password },
    calendars: { 'team': { name, caldav_url, caldav_metadata_url, color }, ... },
    channels: [{ id, name, canvas_id, ..., calendars: ['team', 'vorstand'] }, ...]
  };
}
Shape contract: The returned object must pass the existing validateConfig() checks. This is verified in tests by calling validateConfig(loadConfigFromDb(db, workspaceId)) after seeding.
Workspace-level fields: locale, timezone, error_channel, and nextcloud_url are stored as columns on the workspaces table (not derived from channels). Channels may override locale per-channel. seedWorkspace() reads these from the top-level fields in config.json and writes them to the workspace row.

seedWorkspace(db, workspaceId, configJson)

Imports a parsed config.json object into the new tables. Idempotent (INSERT OR REPLACE throughout). Used for: bootstrapping the abeona workspace on first v2 deploy, and providing test fixtures with known state. 

function seedWorkspace(db, workspaceId, configJson) {
  // 1. upsertWorkspace(db, { teamId: workspaceId, teamName: workspaceId, botToken: null, ... })
  // 2. INSERT OR REPLACE INTO caldav_credentials (workspace_id, username, password)
  // 3. For each calendar in configJson.calendars:
  //      INSERT OR REPLACE INTO calendars (workspace_id, calendar_id, name, caldav_url, ...)
  // 4. For each channel in configJson.channels:
  //      INSERT OR REPLACE INTO channels (workspace_id, channel_id, name, canvas_id, ...)
  //      For each calendarId in channel.calendars:
  //        INSERT OR REPLACE INTO channel_calendars (workspace_id, channel_id, calendar_id)
}

Existing functions kept

  • loadConfig(path) — kept for the seeding path (seedWorkspace(db, id, await loadConfig(path))) and for main branch compatibility.
  • validateConfig(config) — kept; used to verify loadConfigFromDb output in tests.

Caller Updates

All callers that invoke db functions must thread workspaceId through. The config object already carries workspace_id at the top level, so callers use config.workspace_id wherever they call db functions.

server.js

  • Replace await loadConfig(process.env.CONFIG_FILE) with await loadConfigFromDb(db, workspaceId).
  • Read workspaceId from process.env.WORKSPACE_ID (single-workspace mode) — multi-workspace iteration comes in #47.
  • All runScheduledDigests / runChangeDetection calls already receive config and db; the db functions inside runner.js gain the workspaceId arg there.

bot.js

  • Same pattern: loadConfigFromDb(db, workspaceId) replaces loadConfig().
  • WORKSPACE_ID env var required in addition to DATA_DIR.

runner.js

  • Every call to loadEvents, saveEvents, loadColor, saveColor, loadRunState, saveRunState, loadPending, savePending gains config.workspace_id as the second argument.
  • No logic changes — purely a mechanical argument addition.

Acceptance Criteria

  • All existing tables have workspace_id column as part of primary key
  • Schema migration runs cleanly on an old (version 0) database and a fresh database
  • New config tables exist with correct schema and foreign key relationships
  • loadConfigFromDb(db, workspaceId) returns same object shape as current loadConfig()
  • seedWorkspace() imports a config.json object into the new tables
  • seedWorkspace() is idempotent
  • All db.js functions accept and use workspaceId
  • migrateFromFlatFiles is removed
  • All tests pass with ':memory:' database
  • server.js and bot.js use loadConfigFromDb instead of loadConfig
  • runner.js passes config.workspace_id to all db function calls
