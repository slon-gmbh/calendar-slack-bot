Per-Workspace Cron Scheduling

Issue #47
Branch v2
Date 2026-05-21
Priority P0
Size M

Goal: Replace the single-tenant cron setup in server.js (one hardcoded WORKSPACE_ID) with a multi-tenant scheduler that loads all active workspaces from SQLite at startup and dynamically adds or removes jobs when workspaces install or uninstall via Slack OAuth.

Locked Decisions

Architecture

The current server.js reads WORKSPACE_ID from env, calls loadConfigFromDb once, builds a flat jobs array, and passes config directly to every cron handler. This is entirely replaced.

The replacement distributes responsibility across four collaborating modules:

Load-bearing boundary

oauth.js and events.js know nothing about scheduling. They fire callbacks (onInstall, onUninstall) provided by server.js. This means the scheduling logic is fully testable without touching the HTTP layer.

Component Diagram

Lifecycle Diagram

scheduler-registry.js new

Single responsibility: own the Map<workspaceId, CronTask[]> and manage its lifecycle. No HTTP handling, no DB writes, no Slack API calls.

scheduleWorkspace(db, workspaceId, dryRun): void
  • If workspaceId already in JOBS: calls unscheduleWorkspace(workspaceId) first (idempotent re-install)
  • Calls loadConfigFromDb(db, workspaceId) to get channels + schedules
  • For each channel with digest_schedule: registers cron.schedule(expr, handler)
  • For each channel with daily_digest_schedule: registers cron.schedule(expr, handler)
  • Registers one change-detection job at '0 6-18/2 * * *'
  • All tasks stored as JOBS.set(workspaceId, [task1, task2, …])
scheduleAllWorkspaces(db, dryRun): void
  • Calls listActiveWorkspaces(db) — decrypts bot tokens
  • Calls scheduleWorkspace(db, ws.team_id, dryRun) for each
unscheduleWorkspace(workspaceId): void
  • JOBS.get(workspaceId)?.forEach(job => job.stop())
  • JOBS.delete(workspaceId)
  • No-op if workspace not in map
stopAll(): void
  • Stops all jobs across all map entries
  • JOBS.clear()
  • Called by server.js shutdown handler
Error isolation

Each cron handler closure wraps the runner call in try/catch. A crash or rejection for workspace A never stops workspace B's jobs. Log prefix: [cron][workspaceId].

// cron handler pattern (inside scheduleWorkspace)
const handler = async () => {
  console.log(`[cron][${workspaceId}] digest firing for ${channel.id}`);
  try {
    await runScheduledDigests(db, workspaceId, dryRun);
  } catch (err) {
    console.error(`[cron][${workspaceId}] digest error:`, err.message);
  }
};
Why module-scope Map and not a class?

A module-scope Map is the simplest singleton pattern in Node.js — the module cache guarantees a single instance. A class would require passing the registry instance through multiple layers or using a separate singleton export. The module itself is the singleton.

For testing, stopAll() followed by clearing the map provides clean isolation between test cases without needing dependency injection.

events.js new

Handles POST /slack/events. Verifies Slack's HMAC signing signature before processing any event. Currently handles one event type: app_uninstalled.

validateSlackEventsEnvVars(): void
  • Throws if SLACK_SIGNING_SECRET is missing or empty
  • Called in server.js start() alongside validateEncryptionKey() and validateSlackEnvVars()
handleEventsRequest(db, req, res, onUninstall): Promise<boolean>
  • Returns false immediately if method !== 'POST' or pathname !== '/slack/events'
  • Reads raw body bytes (needed for HMAC over original bytes)
  • Checks X-Slack-Request-Timestamp: rejects if >5 min old (replay protection)
  • Verifies X-Slack-Signature: HMAC-SHA256 of v0:${timestamp}:${rawBody} with SLACK_SIGNING_SECRET → 403 if mismatch
  • Parses JSON body
  • type === 'url_verification': responds 200 { challenge }
  • type === 'event_callback' && event.type === 'app_uninstalled': calls markWorkspaceInactive(db, event.team_id), calls onUninstall(event.team_id) if provided, responds 200
  • All other events: responds 200 (acknowledged, ignored)
  • Returns true for all /slack/events POSTs (route was handled)
Security note

Timestamp check (>5min) + HMAC verification together prevent replay attacks. The raw body must be read as bytes before parsing as JSON — any whitespace normalization would invalidate the signature.

Why not add events handling to oauth.js?

oauth.js handles the OAuth 2.0 installation flow. Events is a distinct Slack API surface with different auth (signing secret vs client secret), different request shape, and it will grow as more event types are handled. Keeping them separate keeps both files focused and avoids conflating install-time auth with runtime event delivery.

Added

const registry = require('./scheduler-registry.js');
const { validateSlackEventsEnvVars, handleEventsRequest } = require('./events.js');

async function start() {
  validateEncryptionKey();
  validateSlackEnvVars();
  validateSlackEventsEnvVars();         // new

  const dataDir = process.env.DATA_DIR;
  if (!dataDir) throw new Error('DATA_DIR environment variable not set');
  // WORKSPACE_ID check removed

  const db = openDb(path.join(dataDir, 'bot.db'));
  const dryRun = process.env.DRY_RUN === 'true';

  await registry.scheduleAllWorkspaces(db, dryRun);  // replaces jobs loop

  const onInstall = async (workspaceId) => {
    await registry.scheduleWorkspace(db, workspaceId, dryRun);
  };
  const onUninstall = (workspaceId) => {
    registry.unscheduleWorkspace(workspaceId);
  };

  // HTTP handler adds handleEventsRequest:
  const httpServer = http.createServer(async (req, res) => {
    try {
      if (req.method === 'GET' && req.url === '/health') { /* … */ }
      else if (await handleOAuthRequest(db, req, res, onInstall)) { /* handled */ }
      else if (await handleEventsRequest(db, req, res, onUninstall)) { /* handled */ }
      else { res.writeHead(404); res.end(); }
    } catch (err) { /* 500 handler unchanged */ }
  });

  function shutdown() {
    registry.stopAll();     // replaces: for (const job of jobs) job.stop()
    httpServer.close(() => { db.close(); process.exit(0); });
  }
}

runner.js changes modified

Both exported functions gain one line at the top and drop the config parameter:

// Before:
async function runScheduledDigests(config, db, dryRun) { … }

// After:
async function runScheduledDigests(db, workspaceId, dryRun) {
  const config = loadConfigFromDb(db, workspaceId);
  // rest of function unchanged — config.channels, config.calendars, etc. all still work
}

Same change applies to runChangeDetection. New import added: const { loadConfigFromDb } = require('./config.js').

Why fresh config per invocation?

Config loaded once at startup would be stale if workspace settings change while the server is running. Loading per invocation costs one synchronous SQLite read — negligible for digest/change-detection frequency. It also simplifies the caller (no config object to carry around).

oauth.js changes modified

The only change is accepting an optional onInstall callback and calling it after a successful install:

// Before:
async function handleOAuthRequest(db, req, res) { … }

// After:
async function handleOAuthRequest(db, req, res, onInstall) {
  // …on successful token exchange:
  upsertWorkspaceFromOAuth(db, { teamId, teamName, botToken, installedBy });
  if (onInstall) await onInstall(teamId);  // replaces TODO #48 comment
  res.writeHead(302, { Location: '/slack/install/success' });
  res.end();
}

onInstall is optional — existing tests that call handleOAuthRequest(db, req, res) without the fourth argument continue to work.

db.js changes modified

One new function added after listActiveWorkspaces:

function markWorkspaceInactive(db, teamId) {
  db.prepare('UPDATE workspaces SET active = 0 WHERE team_id = ?').run(teamId);
}

Added to module.exports.

Acceptance Criteria

  • On startup, cron jobs registered for all active workspaces from SQLite
  • New workspace install dynamically adds cron jobs (no process restart needed)
  • Workspace uninstall (via Slack app_uninstalled event) stops their cron jobs and marks workspace inactive in DB
  • Each workspace's jobs use their own bot token and config loaded from DB
  • Zero cross-workspace data leakage in any cron execution
