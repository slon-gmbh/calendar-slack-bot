Slack Slash Command Handler

POST /slack/commands — receive and dispatch /calendar subcommands with HMAC verification, per-workspace DB lookups, and Block Kit responses.

Overview

This feature adds a POST /slack/commands HTTP endpoint to the multi-tenant Fly.io server. It handles the /calendar slash command that Slack delivers to registered apps, routing four subcommands (help, config, status, refresh) to per-workspace handlers.

As a by-product, the HMAC-SHA256 verification logic that currently lives inline in src/events.js is extracted into a shared src/slack-verify.js module so both endpoints use the same tested code path.

Scope boundary: This spec covers request verification, routing, and read-only responses only. Mutating workspace config (editing schedules, adding calendars) is out of scope — that belongs to issue #29 (edit channel settings modal).

Locked Decisions

DecisionChoiceRationale

Command handler location New file src/commands.js Keeps server.js as a thin router; logic isolated and testable.
Response visibility Ephemeral (caller only) Config/status output is noisy in public channels.
Refresh execution model Async with response_url callback Slack requires a response within 3 s; change detection can take longer.
Refresh authorisation Any workspace member Refresh is read-only in effect. Admin check deferred until write commands exist.

Architecture

New Files

src/slack-verify.js new

Pure verification utilities. Exports two functions: verifySlackRequest(rawBody, timestamp, signature, secret) — synchronous, returns boolean; and readAndVerify(req, secret) — async, reads the raw request body, checks the timestamp window, verifies the HMAC, and returns { rawBody, parsedBody } (where parsedBody is the URL-decoded object). Throws { statusCode: 403 } on failure so callers can send the right HTTP response without coupling verification to HTTP.

src/commands.js new

Slash command handler. Exports handleSlashCommand(db, req, res) (returns Promise<boolean> — true if handled, false otherwise) and validateSlackCommandsEnvVars() (throws if SLACK_SIGNING_SECRET is missing). Handles routing, DB lookup, subcommand dispatch, and Block Kit response construction.

Request Flow

Step-by-step flow description
  1. Receive — POST /slack/commands arrives at server.js.
  2. Route — handleSlashCommand(db, req, res) is called; returns false for any non-POST /slack/commands request.
  3. Verify — readAndVerify(req, secret) reads the raw body, checks x-slack-request-timestamp is within 300 s, and verifies the x-slack-signature HMAC. Sends 403 and returns on failure.
  4. Parse — body decoded as application/x-www-form-urlencoded: extract team_id, channel_id, user_id, command, text, response_url.
  5. Workspace lookup — getWorkspace(db, team_id). If not found: 200 ephemeral "Workspace not configured yet."
  6. Route subcommand — first whitespace-delimited token of text. Unknown token: 200 ephemeral "Unknown command. Try /calendar help."
  7. Respond — 200 with application/json Block Kit payload (response_type: "ephemeral"). For refresh: send ack immediately, run detection asynchronously, POST result to response_url.

Subcommands

All responses use response_type: "ephemeral". Responses are visible only to the user who ran the command.

/calendar help

Returns a single section block with a fixed listing of available commands.

{
  "response_type": "ephemeral",
  "blocks": [
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "*Available commands:*\n`/calendar help` — show this help\n`/calendar config` — show channel calendar setup\n`/calendar status` — show last digest run times\n`/calendar refresh` — run calendar change detection now"
      }
    }
  ]
}

/calendar config

Calls loadConfigFromDb(db, teamId). For each channel in the workspace config, renders a section block showing:

  • Channel name (or ID if name absent)
  • Digest schedule (digest_schedule field, or "disabled")
  • Daily digest schedule (daily_digest_schedule field, or "disabled")
  • Linked calendar names (from the calendars array)

If no channels are configured, or loadConfigFromDb throws: 200 ephemeral "No calendars configured for this workspace."

Example Block Kit payload 
{
  "response_type": "ephemeral",
  "blocks": [
    {
      "type": "header",
      "text": { "type": "plain_text", "text": "Calendar Config — My Workspace" }
    },
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "*#general*\nDigest: `monday 09:00`\nDaily: disabled\nCalendars: Team Calendar, Holidays"
      }
    },
    { "type": "divider" },
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "*#events*\nDigest: `friday 08:00`\nDaily: `08:00`\nCalendars: Public Events"
      }
    }
  ]
}

/calendar status

Calls loadRunState(db, workspaceId, channelId, digestType) for each channel × type ('weekly', 'daily'). Returns a section per channel showing last run timestamps (ISO string, or "never" if null).

Example Block Kit payload 
{
  "response_type": "ephemeral",
  "blocks": [
    {
      "type": "header",
      "text": { "type": "plain_text", "text": "Bot Status — My Workspace" }
    },
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "*#general*\nLast weekly digest: `2026-05-25T09:00:00.000Z`\nLast daily digest: never"
      }
    }
  ]
}

/calendar refresh

Two-phase response to stay within Slack's 3-second window:

  1. Immediate 200 ack — body: {"response_type":"ephemeral","text":"Refreshing calendars…"}
  2. Async detection — calls runChangeDetection(db, teamId, false) in the background. On completion, POSTs to response_url:
    • Success: {"response_type":"ephemeral","text":"Change detection complete."}
    • Error: {"response_type":"ephemeral","text":"Change detection failed: <message>"}

The response_url POST uses Node's built-in node:https module (no additional dependencies). The async block is fire-and-forget from the HTTP handler's perspective — errors in the async block are caught and logged, never bubble to the request handler.

Error Handling

ConditionResponseNotes
Non-POST method or path ≠ /slack/commands return false Not handled; server.js falls through to next handler.
Stale timestamp (> 300 s) 403 (empty body) Replay-attack prevention.
Bad or missing x-slack-signature 403 (empty body) HMAC mismatch.
Workspace not found in DB 200 ephemeral — "Workspace not configured yet." Workspace may have uninstalled after the command was typed.
Unknown subcommand 200 ephemeral — "Unknown command. Try /calendar help." Catches empty text and unrecognised tokens.
loadConfigFromDb throws 200 ephemeral — "Could not load workspace config." Logged to console; error not surfaced to user verbatim.
runChangeDetection throws (refresh) POST to response_url: "Change detection failed: <message>" Error message is safe to surface — it comes from our own runner.
POST to response_url fails Logged, silently dropped response_url is only valid for 30 min. Log at warn level.

Testing

Framework: node:test + node:assert. Run with NODE_ENV=test node --test test/*.test.js.

test/slack-verify.test.js new

  • Valid signature and fresh timestamp → returns { rawBody, parsedBody }
  • Stale timestamp (> 300 s) → throws { statusCode: 403 }
  • Wrong signature → throws { statusCode: 403 }
  • Missing x-slack-request-timestamp header → throws { statusCode: 403 }
  • verifySlackRequest (pure): valid returns true, tampered body returns false

test/commands.test.js new

  • Bad signature → 403
  • Workspace not found → 200 ephemeral with "not configured" text
  • /calendar help → 200, payload contains all four command names
  • /calendar config → 200, payload contains channel name and schedule fields
  • /calendar status → 200, payload contains "Last weekly digest" text
  • /calendar refresh → immediate 200 ack with "Refreshing" text
  • /calendar refresh → calls runChangeDetection asynchronously
  • Unknown subcommand (foobar) → 200 with "Unknown command" text
  • Empty text → 200 with "Unknown command" text
  • Non-POST → returns false

Existing 10 tests must remain green after events.js is refactored to use slack-verify.js. No new tests required — the shared verification is covered by slack-verify.test.js.
